Diseño de infraestructura · AWS EKS

Un cluster, todos los proyectos

Explicación detallada de la plataforma diseñada para desplegar quiz, invoicing-service, invoicing-app y el resto del portafolio sobre un único cluster EKS de bajo costo, con GitOps y despliegues independientes por aplicación.

1 cluster · 1 entorno nodos AMD64 SPOT ArgoCD GitOps Terraform + módulos oficiales ALB compartido ~134 USD/mes
§1

Contexto

Hoy cada proyecto se despliega de forma distinta y, en su mayoría, manual. Tres plataformas de cómputo conviviendo sin necesidad, y ningún camino repetible para las aplicaciones que aún faltan por incorporar.

ProyectoCómputo actualCIManifiestos k8s
quizECS Fargate vía Terraform localningunaninguno
invoicing-serviceAWS App Runner vía Terraform4 workflows GitHub ActionsKustomize base + overlay local
invoicing-appS3 + CloudFront vía script manualningunaninguno

A eso se suma estado de Terraform versionado dentro de los propios repos (quiz/infra/terraform/terraform.tfstate, invoicing-service/terraform.tfstate), un Load Balancer o una distribución por aplicación, y siete proyectos hermanos con el mismo patrón backend Spring Boot + frontend Vite (planner-pocker, your-are-invited, project-intelligence-platform, delivery-ops…) sin ningún lugar común donde aterrizar.

Objetivo

Un cluster EKS único y de bajo costo con una plataforma compartida — ingress, secretos, observabilidad, GitOps — sobre la que cada aplicación se despliega de forma independiente. El onboarding de una app nueva se reduce a: escribir un deploy/values.yaml, añadir un workflow de diez líneas y registrar una Application de ArgoCD.

§2

Tres capas: entrada única por un ALB compartido, cómputo en un cluster EKS con un namespace por aplicación, y los servicios de datos de AWS alcanzados por IRSA — sin llaves de acceso estáticas en ningún punto.

Los namespaces con borde punteado (invoicing, planner-poker) representan el estado planeado para la segunda ola — hoy solo existe quiz, la aplicación piloto. Cada namespace de aplicación es autónomo: su propio Deployment, su propio Ingress dentro del mismo grupo de ALB, su propio ExternalSecret.

§3

Red

VPC de dos zonas de disponibilidad. La decisión que más pesa en el costo mensual: sin NAT Gateway.

BloqueTipoContenido
10.0.0.0/20Pública · us-east-1aNodos EKS, ALB
10.0.16.0/20Pública · us-east-1bNodos EKS, ALB
10.0.64.0/20Privada · us-east-1aRDS PostgreSQL
10.0.80.0/20Privada · us-east-1bRDS PostgreSQL (subnet group)

Los nodos viven en subnets públicas con IP propia; el VPC CNI hace SNAT del tráfico saliente de los pods, así que el pull de imágenes y las llamadas a APIs externas (Cognito, SMTP, Hacienda SV) funcionan sin NAT Gateway. Ahorro: ~32 USD/mes.

Mitigación obligatoria

El security group de los nodos no abre ningún puerto de entrada desde 0.0.0.0/0: solo acepta tráfico del SG del ALB y de sí mismo. Sin acceso SSH — la única vía administrativa es la API de EKS (kubectl), el node group se crea con remote_access = null.

enable_nat_gateway = true queda disponible como variable para mover los nodos a subnets privadas el día que el proyecto lo justifique — un cambio de una línea y un terraform apply, a costa de ~35 USD/mes adicionales. Un endpoint de S3 tipo Gateway (gratis) evita que el tráfico de Loki y de las capas de ECR salga a internet.

§4

Cluster

Un control plane gestionado por AWS y un único managed node group en modo SPOT, diversificado entre tres tipos de instancia para reducir la probabilidad de interrupción simultánea.

Versión1.33
AutenticaciónEKS Access Entries (API) — no el aws-auth ConfigMap legado
Endpointpúblico + privado, restringido por CIDR
Addons gestionadosvpc-cni · coredns · kube-proxy · aws-ebs-csi-driver
Node groupSPOT, t3.medium / t3a.medium / t2.medium, 2–4 nodos, AMD64 exclusivo (AL2023_x86_64_STANDARD)

Con dos nodos como mínimo, el cluster tolera la pérdida de uno sin quedarse sin capacidad. Karpenter queda fuera de esta fase: un node group fijo es más simple y, a esta escala, no hay nada que Karpenter ahorre — se reconsidera al superar unas seis aplicaciones desplegadas.

§5

Ingress — el punto que decide el costo

El AWS Load Balancer Controller consolida los Ingress de todas las aplicaciones en un único ALB mediante la anotación group.name. Sin esto, cada app pagaría su propio Load Balancer a ~18 USD/mes. 

alb.ingress.kubernetes.io/group.name: shared
alb.ingress.kubernetes.io/target-type: instance
alb.ingress.kubernetes.io/scheme: internet-facing
# quiz ya lo anticipa: Dockerfile:11 expone ARG VITE_BASE_PATH

Sin dominio propio, el ruteo es por path sobre el hostname del ALB:

PathDestino
/quiz/*Service quiz, namespace quiz
/invoicing/*frontend invoicing-app
/api/invoicing-management/*backend invoicing-service

quiz ya está preparado para esto: acepta SERVER_SERVLET_CONTEXT_PATH (application.yml:30) y su Dockerfile ya declara VITE_BASE_PATH pensando justamente en un ALB compartido.

§6

Secretos

External Secrets Operator hace de puente hacia AWS Secrets Manager, con IRSA — el mismo modelo mental que ambos proyectos ya usan hoy, solo cambia el mecanismo de inyección.

1

AWS Secrets Manager

Un secreto por app: eks/<app>, claves como JSON.

2

ExternalSecret (namespace de la app)

Referencia el ClusterSecretStore compartido, extrae todas las claves.

3

Secret nativo de Kubernetes

Materializado y refrescado cada hora por el operador.

4

Pod · envFrom.secretRef

El contenedor lo consume como variables de entorno, sin cambios en la app.

Precedente directo: AwsSecretsEnvironmentPostProcessor.java:83 en invoicing-service resuelve invoicing-service/<perfil>, y quiz/infra/terraform/main.tf:39-75 ya define tres secretos equivalentes para ECS.

§7

Datos

Una instancia RDS PostgreSQL compartida por las aplicaciones que usan Postgres. Las bases y usuarios individuales se crean a mano.

MotorPostgreSQL 16
Clasedb.t4g.micro
Almacenamiento20 GB gp3
Disponibilidadsingle-AZ, backups 7 días
Redsubnets privadas, SG solo acepta 5432 desde el SG de nodos
Credencial maestrarandom_password → Secrets Manager, nunca en el estado en claro
Advertencia — invoicing-service usa MySQL

No PostgreSQL. Su pom.xml trae mysql-connector-j y flyway-mysql, y su multi-tenancy schema-per-tenant corre por un TenantFlywayRunner propio. El RDS Postgres compartido no le sirve. Cuando entre al cluster hará falta una segunda instancia RDS MySQL db.t4g.micro (~13 USD/mes adicionales) — migrar el motor no es viable a corto plazo por el acoplamiento del multi-tenancy. El módulo de datos ya se diseñó pensando en aceptar n motores.

§8

Observabilidad

Stack self-hosted: métricas y logs adentro del cluster, sin depender de CloudWatch para no disparar el costo de ingesta.

  • kube-prometheus-stack — Prometheus con retención de 7 días sobre un PVC gp3 de 10 GB, más Grafana y Alertmanager.
  • Loki — modo SingleBinary, backend en S3 con expiración a 14 días en vez de PVC.
  • Grafana Alloy — agente de recolección de logs hacia Loki.
  • metrics-server — base para kubectl top y para el HPA.
  • ServiceMonitor — el chart genérico lo crea automáticamente cuando metrics.enabled: true, recolectando las métricas Micrometer de los backends Spring Boot.
Sin TLS, sin exposición

Grafana y ArgoCD se acceden por kubectl port-forward, nunca por el ALB. Sin dominio propio no hay certificado válido, y publicar un panel de administración sobre HTTP plano en internet expondría credenciales en claro. Con dominio y cert-manager esto se resuelve en una fase posterior.

El chart y los values.yaml se unen en tiempo de sincronización mediante una Application de ArgoCD multi-source — evita publicar el chart en un registry OCI y lidiar con la expiración a 12 horas del token de ECR: 

# argocd/applications/quiz.yaml
spec:
  sources:
    - repoURL: https://github.com/jairoeduardov/eks.git
      targetRevision: main
      path: charts/app
      helm:
        releaseName: quiz
        valueFiles: [$values/deploy/values.yaml]
    - repoURL: https://github.com/jairoeduardov/quiz.git
      targetRevision: main
      ref: values
  syncPolicy:
    automated: { prune: true, selfHeal: true }

Así el chart se versiona y evoluciona en un solo lugar, pero cada aplicación mantiene la propiedad de su configuración y de su tag de imagen.

§10

Chart genérico

Un solo chart Helm cubre los tres arquetipos del portafolio, parametrizado por values.yaml.

CasoEjemploConfiguración clave
Monolito Spring Boot con frontend embebido quiz, planner-pocker, your-are-invited un release, puerto 8080, probes de actuator
Backend + frontend separados invoicing-service + invoicing-app dos releases del chart, comunicados por DNS interno del Service
Servicio interno sin exposición colas, workers ingress.enabled: false 
image: { repository: "", tag: "" }
containerPort: 8080

# ruteo sobre el ALB compartido
ingress:
  group: shared
  paths: ["/quiz"]
  healthcheckPath: /quiz/actuator/health

resources:
  requests: { cpu: 200m, memory: 512Mi }
  limits:   { memory: 1Gi }   # sin limite de cpu, a proposito

externalSecret:
  secretName: eks/quiz

Sobre resources: se fija limits.memory pero deliberadamente no limits.cpu. Limitar CPU en aplicaciones JVM produce throttling del CFS que degrada latencias de forma difícil de diagnosticar; el requests.cpu ya garantiza la porción justa bajo contención.

§11

Pipeline de despliegue

Cada push a main del repo de una aplicación dispara su propio flujo, sin tocar a ninguna otra app.

01

Build + test

En el runner del repo de la app.

02

docker buildx --platform linux/amd64

Siempre AMD64, sin excepción.

03

Trivy scan

Falla el pipeline si hay CRITICAL con fix disponible.

04

OIDC → push a ECR

Sin llaves estáticas. Tags: SHA corto y main-latest.

05

Bump de deploy/values.yaml

Commit chore: deploy <sha> [skip ci] en el mismo repo.

06

ArgoCD sincroniza

Detecta el commit en menos de 3 minutos — prune + selfHeal automáticos.

Puntos de diseño

  • Sin llaves estáticas. GitHub OIDC asume un rol de IAM restringido por repo:jairoeduardov/*:ref:refs/heads/main. Precedente ya en uso: invoicing-service/.github/workflows/deploy-dev.yml.
  • El bucle de CI se corta por dos vías a la vez — [skip ci] en el commit y paths-ignore: ['deploy/**'] en el trigger — porque el primero no aplica si alguien dispara con workflow_dispatch.
  • El tag nunca es latest. Siempre el SHA corto del commit. Un rollback es revertir el commit de deploy/values.yaml; ArgoCD lo sincroniza solo.
  • Independencia total. Cada app tiene su repo, su workflow, su ECR, su namespace, su Application y su values.yaml. Es el requisito central del diseño.

Lo único que se escribe al hacer onboarding de una app nueva:

# quiz/.github/workflows/deploy.yml
on:
  push:
    branches: [main]
    paths-ignore: ['deploy/**']
jobs:
  deploy:
    uses: jairoeduardov/eks/.github/workflows/app-build-deploy.yml@main
    with:
      app_name: quiz
    secrets: inherit

§13

Piloto: quiz

El mejor candidato para validar toda la plataforma: un solo contenedor, frontend embebido en el jar, RDS externo, sin colas ni cache. Siete cambios concretos:

  1. 01
    Habilitar probes de Kubernetesmanagement.endpoint.health.probes.enabled: true en application.yml — sin esto, /actuator/health/liveness devuelve 404 y el pod nunca llega a Ready.
  2. 02
    Nuevo deploy/values.yamlcon SERVER_SERVLET_CONTEXT_PATH: /quiz.
  3. 03
    Nuevo .github/workflows/deploy.ymldiez líneas — la primera CI que tendrá el repo.
  4. 04
    Secreto eks/quiz en Secrets Managermigrado desde los tres secretos que ya crea infra/terraform/main.tf:39-75.
  5. 05
    Base de datosCREATE DATABASE quiz en el RDS compartido y restaurar un dump — Flyway corre las 14 migraciones al arrancar.
  6. 06
    Arquitectura de imagenel Dockerfile no fija plataforma; un runner ubuntu-latest ya produce AMD64 sin tocar nada.
  7. 07
    ECS queda intactohasta validar EKS en producción, luego se retira junto con su terraform.tfstate versionado.

Verificación end-to-end

El control plane (73 USD/mes) es fijo e irreducible — más de la mitad del costo total y el piso de cualquier cluster EKS. Cada aplicación adicional que quepa en los nodos existentes es prácticamente gratis: ese es el argumento económico de consolidar el portafolio acá en vez de mantener un App Runner o una distribución CloudFront por proyecto. Activar enable_nat_gateway sumaría ~35 USD/mes más.

§17

Riesgos y deuda identificada

invoicing-service usa MySQL, no PostgreSQL

Diseño

Requiere una segunda instancia RDS antes de que ese servicio entre al cluster. Ya contemplado en el módulo de datos.

Bug en invoicing-app/Dockerfile.frontend

Bloqueante

Declara los ARG VITE_* pero nunca los promueve a ENV antes de pnpm build — Vite no los lee y el bundle sale apuntando a localhost. Corregir antes de desplegar ese frontend.

Credenciales reales en el árbol de trabajo

Seguridad

invoicing-service/k8s/overlays/local/app-secret.yaml existe junto a su .example. Verificar que no esté trackeado en git y rotar lo que haya quedado expuesto.

Estado de Terraform versionado en los repos

Higiene

quiz/infra/terraform/terraform.tfstate e invoicing-service/terraform.tfstate pueden contener secretos en claro. Migrar al backend S3 y purgar del historial.

CI de invoicing-service no prueba nada

Calidad

El paso "Run tests" de ci.yml corre con -DskipTests. Además requiere Java 25 + GraalVM en el runner.

SPOT sin diversificar puede perder ambos nodos a la vez

Operación

Mitigado con tres tipos de instancia y PodDisruptionBudget opcional. Si molesta, mover un nodo a ON_DEMAND cuesta ~15 USD/mes más.

Sin dominio no hay TLS válido

Aceptado para lab

El tráfico al ALB viaja en HTTP plano, incluidas cookies de sesión y tokens de Cognito. Aceptable en laboratorio, no para datos reales de terceros. Un dominio + ACM + cert-manager es el siguiente paso natural (~12 USD/año).
